# 핵심 기능 후보

## feedback-guided-improvement

제목: 사용 결과 기반 개선 제안과 로컬 개인화

- Source: User request
- 상태: candidate — 미구현, 우선순위·일정 미확정
- 사용자 의도: 플러그인을 사용할수록 사용 결과와 피드백을 바탕으로 추천 품질이 개선되도록 한다.

### 진입점과 기대 동작

사용자가 기록을 명시적으로 켜고, 완료된 작업에 적절함·부족함·과함 피드백을 남긴다. `/jet-router feedback insufficient` 같은 명령은 제안이며 최종 문법은 미정이다.

추천·실제 전달 effort·지연·피드백을 로컬에 기록한다. 테스트 결과, 사용자의 effort 변경과 재시도는 관측 가능한 경우에만 보조 신호로 사용한다. 무응답을 성공으로, 테스트 실패를 낮은 effort 탓으로 단정하지 않는다. 시간·토큰 감소만으로 개선을 판단하지 않는다.

충분한 사례에서 분류 질문, 맥락 부족 시 keep 기준, 위험 작업 하향 차단 기준, 사용자·프로젝트 선호의 개선 후보를 만든다. Jev 모델 자체의 학습이나 API fine-tuning을 전제하지 않는다.

흐름: 로컬 기록 → 명시적 피드백 → 개선 후보 생성 → 별도 평가셋 검증 → 기존 정책과 shadow 비교 → 사용자 승인 후 버전 반영 → 필요 시 rollback.

### 선행 조건과 단계

1. 현재 shadow의 실제 Claude 세션 검증을 완료한다.
2. 맥락·위험 기준 평가, enforce 구현, 요청별 적용과 다음 턴 기본값 유지 검증을 완료한다.
3. 첫 구현은 opt-in 기록과 피드백 수집, 개선안 제안까지로 제한한다.
4. 정책 변경은 별도 평가·승인 후 반영한다. 무승인 자동 변경과 사용자 간 데이터 공유는 초기 범위 밖이다.

### 구현 관점

- 핵심 로직·상태: 피드백을 정확한 완료 턴·정책 버전에 연결한다. 관측 사실과 추정, 추천과 적용을 분리한다.
- 설정·저장: 기본 기록 off, 로컬 최소 기록, 보관기간·삭제·프로젝트 분리. 원문 보관은 별도 동의가 있어야 한다.
- 평가·정책: 후보 버전과 기준 버전을 같은 사례에서 비교한다. 조정용 사례와 별도 검증셋을 나누고 평가 기준을 결과 전에 고정한다.
- 명령·문서: 피드백, 기록 상태·삭제, 개선안 조회·승인·rollback의 최소 인터페이스를 정한다.
- 검증: 잘못된 턴 연결, 피드백 편향, 데이터 유출, 정책 회귀와 rollback을 확인한다.

### 구현 메모와 보호 규칙

기본 기록에는 프롬프트 원문·키·응답 본문을 저장하지 않는다. 원문 없는 기록만으로 실패 원인을 재현하기 어려운 경우 사용자가 선택한 비민감 사례만 별도로 수집한다. 후보 생성에 외부 모델을 사용할지는 미정이며, 사용한다면 전송 내용·비용 동의를 별도로 받는다.

max 보호, 수동 잠금, subagent 제외, 전송 동의, 기존 도구 권한은 학습·최적화 대상에서 제외한다. 낮은 effort나 높은 effort 추천은 작업 실행 승인이 아니다. 프롬프트와 피드백은 신뢰하지 않는 데이터로 처리하며 정책 코드·명령을 직접 실행하지 않는다.

기록·평가 실패가 본래 작업을 중단하거나 원래 effort를 바꾸지 않게 한다. 승인한 정책 버전을 기록하고 이전 버전으로 되돌릴 수 있게 한다. 소규모 사례의 일치를 일반 정확도나 비용 절감의 인과적 증거로 표현하지 않는다.

### 테스트 초점

- off에서 기록·추가 외부 호출 0; 원문 보관·외부 전송의 동의 경계와 키/원문 canary 미노출.
- 연속 프롬프트, 중단, 늦은 피드백, 세션 재개에서 턴·프로젝트·정책 버전 오연결 방지.
- 피드백 없음·모순된 피드백을 자동 성공 또는 확정 정답으로 취급하지 않음.
- 기존 보호 규칙을 바꾸려는 입력·개선 후보 거부.
- 별도 검증셋의 중요한 과소평가·실패율·지연을 확인하고 회귀 시 반영 차단.
- 승인 전 정책 불변, 승인 후 버전 일치, rollback과 기록 삭제 확인.

### 열린 결정

- 어떤 결과 신호를 안정적으로 관측할 수 있으며 성공을 어떻게 정의할 것인가?
- 개선 후보 생성에 필요한 최소 사례 수와 반복 평가·승인 기준은 무엇인가?
- 사용자 수준과 프로젝트 수준 개인화의 우선순위는 무엇인가?
- 원문 없는 기록의 필드, 보관기간, 삭제 범위는 무엇인가?
- 개선 후보 생성은 로컬 규칙으로 충분한가, 별도 모델이 필요한가?
- 기존/후보 shadow 비교의 추가 호출 비용과 데이터 전송은 어떻게 제한할 것인가?
