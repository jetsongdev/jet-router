## 해석

1. **Q1: 문서 규칙과 다르다.** top-level effort만 바꿔도(A1) messages 캐시는 깨지지 않았다. 변경 턴은 직전 prefix의 99.7% 이상을 읽었다. 유일한 차이는 A1 복귀 턴(턴4)이다. 직전 턴(high)에서 새로 쓴 꼬리(약 60 tokens)를 medium에서 읽지 못하고 다시 썼다(쓰기 100–112 vs A0 42–55, diagnostics `cache_miss_reason: unavailable`). 다른 effort로 쓴 마지막 구간만 재사용이 안 되는 것으로 보이며, 비용은 무시할 수준이다.
2. **Q2: 메시지 방식(A2·A3·A6)도 유지된다.** Claude Code 내부 beta 이름 `per-turn-control-2026-07-01`도 공개 API에서 200으로 수락됐다.
3. **Q3(실제 경로)와의 결합:** B1에서 확인한 Claude Code 요청 형태(top-level + 메시지 동시 변경)를 재현한 A6에서도 캐시가 유지됐다. 이는 기존 관찰(B0: 적용 첫 요청의 prefix 전체 재기록 0/25)과 일치한다. **현재 jet-router enforce의 적용·복귀 턴은 캐시를 깨지 않는다고 판단한다**(Opus 5.5, 2026-10-29 시점).

## 한계

- 과제가 짧아 출력이 12–67 tokens였고, thinking 블록은 거의 없거나 생략됐다. 실제 Claude Code 턴처럼 긴 thinking 블록이 이력에 있을 때도 같은지는 이 실험이 직접 보이지 않는다. B0 관찰이 그 조건을 간접적으로 덮는다.
- effort가 서버에서 실제로 적용됐는지는 출력 토큰만으로 확인할 수 없다(과제가 너무 쉬움). 이 실험은 캐시만 판정한다.
- A6은 thinking 필드를 생략한 상태로 진행했다(`display: "updates"`는 공개 API에서 beta 없이 거부됨). Claude Code는 이 값을 보낸다(B1). 그래서 thinking 설정까지 같은 재현은 아니다.
- 1시간 TTL(Claude Code 기본)이 아니라 5분 TTL로 측정했다.
- A3·A4·A6b는 반복 5회 미만이라 기술 관찰이다.
